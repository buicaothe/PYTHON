Algorithms Implemented

Sorting

  • Bubble Sort — O(n²), stable, early-exit on sorted input.
  • Insertion Sort — O(n²), stable, few swaps on nearly-sorted data.
  • Merge Sort — O(n log n) all cases, stable.

Searching

  • Linear Search — O(n), works on any list.
  • Binary Search — O(log n), iterative and recursive variants (requires sorted input).

Tree Traversals

  • In-order, Pre-order, Post-order — recursive and explicit-stack iterative.
  • Level-order (breadth-first) using the project's own QueueLinked.

All sorting/searching functions accept an optional OpStats counter for comparisons and swaps.

Hashing: Functions & Collision Resolution

Hash functions (from scratch)

  • division_hash — key % table_size (integer keys).
  • polynomial_hash — Horner's method, base 31 (string keys).
  • djb2_hash — classic djb2 (string keys).

Collision resolution

  • Separate chaining — plain-list buckets, grow-only resizing at load factor 0.75.
  • Open addressing — linear and quadratic (triangular) probing, tombstone deletions.

Both tables track collision count and resize count, and are demonstrated against integer IDs and string names.

Key Finding: Balanced Trees Matter

Inserting IDs 1–20 in sorted order:

  • BST height: 19 — degenerates into a linked list. Search becomes O(n).
  • AVL height: 4 — self-balancing keeps search O(log n).
BST (sorted input):
1
└── 2
└── 3
...
└── 20 (height 19)

AVL (same input):
balanced tree, height 4

Lesson: Always prefer a balanced tree (AVL) when input order cannot be controlled.

Performance: Sorting Algorithms Compared

Wall-clock time across input sizes and distributions (random, sorted, reverse, duplicates).

  • Merge sort — consistently fastest for medium/large inputs (O(n log n)), unaffected by distribution.
  • Insertion sort — competitive on tiny or nearly-sorted inputs; O(n²) otherwise.
  • Bubble sort — simplest but slowest in practice; O(n²) with more swaps than insertion sort.

Recommendation: Use merge sort for general-purpose sorting; insertion sort only for tiny/nearly-sorted data.

Performance: Tree Traversals

Recursive vs explicit-stack iterative traversals (in-order, pre-order, post-order).

  • Both produce identical sequences; both run in O(n) time.
  • Recursive: O(h) call-stack space. Iterative: O(h) explicit-stack space.
  • On balanced trees h = O(log n); on skewed BSTs h = O(n), so recursion depth can become a practical limit.

Recommendation: Choose recursive for clarity; iterative when stack depth is a concern.

Challenges Faced

  • No built-in containers: Could not use dict/set in hash tables or list.sort in sorting — everything built from nodes, buckets, and slots.
  • Plain-list discipline: Restricted raw [None] * capacity lists to backing storage only; every other structure uses its own primitives.
  • AVL rebalancing without parent pointers: Used recursive return values to propagate new subtree roots and apply rotations on the unwind.
  • Open-addressing deletions: Needed tombstone sentinels so removing a key never breaks a later probe sequence.
  • Quadratic probing coverage: Plain i^2 probing visits only ~half the slots of a power-of-two table; switched to triangular numbers for full coverage.

Lessons Learned

  • Balance is not optional: an unstructured BST degrades to O(n) on sorted input; a balanced tree guarantees O(log n).
  • Algorithm choice depends on input: insertion sort beats merge sort only on tiny/nearly-sorted data; merge sort wins generally.
  • Hash-table tuning matters: load factor, hash-function quality, and collision strategy all affect real-world performance.
  • Recursive vs iterative: same asymptotic result, but iterative avoids stack-depth limits on skewed trees.
  • Document complexity alongside code: Time/Space docstrings on every method make the analysis self-documenting.
